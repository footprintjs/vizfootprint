# Derived columns as declared transforms — what the grammars teach vizfootprint

Layer named: **1 data (computation), shown through layer 4 (interaction grammar) and 5 (agent why())**. All claims cite what I fetched; the Wrangler paper text came only through a search-result abstract, so its finer points are marked [unverified].

## 1. The shapes on offer

**A. Expression STRING in a sandboxed mini-language (Vega / Vega-Lite).** Vega-Lite's `calculate` is `{"calculate": "<expression string>", "as": "<field>"}` where the string uses the Vega expression language and `datum` names the current row (https://vega.github.io/vega-lite/docs/calculate.html). That language is a restricted JavaScript subset: "assignment operators (=, += etc), pre/postfix updates (++), new expressions, and most control flow statements (for, while, switch, etc)" are not allowed, nested method calls like `foo.bar()` are refused, and it is parsed and code-generated by vega-expression rather than `eval()` (https://vega.github.io/vega/docs/expressions/). Vega-Lite's `filter` is two-faced: an expression string OR a structured field predicate (`equal|lt|lte|gt|gte|range|oneOf|valid`) with and/or/not composition (https://vega.github.io/vega-lite/docs/filter.html). The window transform is pure data: `{"window":[{op, field, param, as}], frame, groupby, sort, ignorePeers}` with `row_number|rank|dense_rank|lag|lead|first_value|nth_value…` plus every aggregate op (https://vega.github.io/vega-lite/docs/window.html). Transforms run "in the order in which they are specified in the array" (https://vega.github.io/vega-lite/docs/transform.html).

**B. Parsed FUNCTION bodies (Arquero).** `derive({ sumXY: d => d.x + d.y })` takes real JS, but Arquero "takes a set of function definitions, maps them to strings, then parses, rewrites, and compiles them"; "internal function definitions, variable updates, and for loops" are refused, "parsed table expressions do not support closures", external values enter only via `params()`, and only functions from the `op` namespace are callable. `escape()` runs a raw function directly but loses aggregate/window support and breaks serialization (https://idl.uw.edu/arquero/api/expressions). That serialization is real: arquero-worker converts verbs to an AST and ships them to a worker thread, and `escape()`/closures are unsupported there (https://github.com/uwdata/arquero-worker). The verb list (derive/filter/groupby/rollup/orderby/lookup/fold/pivot/join…) documents no SQL output (https://idl.uw.edu/arquero/api/verbs).

**C. NAMED reducers as data (Observable Plot).** `Plot.groupX({y: "sum"}, {x: "species", y: "body_mass_g"})` — outputs map channels to reducer NAMES (`count|sum|mean|median|min|max|first|last|proportion|mode|variance|deviation|pXX`), and only as an escape hatch a function or an object with `reduceIndex` (https://raw.githubusercontent.com/observablehq/plot/main/docs/transforms/group.md). Names are data; functions are code.

**D. Pipeline verbs compiled to SQL (dplyr/dbplyr, PRQL, Malloy).** dbplyr "aims to translate the most common R functions to their SQL equivalents"; a `mutate(a = y*x, b = a^2)` becomes a nested `SELECT … POWER(a, 2.0) AS b FROM (SELECT … y * x AS a …)` — a derived column that refers to another derived column is automatically a subquery; `show_query()` shows the SQL; "Any function that dbplyr doesn't know about will be left as is" (https://dbplyr.tidyverse.org/articles/sql.html). PRQL is a pipeline (`from → filter → derive → group → aggregate → sort → take`) in which `derive` "adds columns / variables" and later columns may reference earlier ones; it compiles `filter artist == "Bob Marley" | aggregate {plays = sum plays}` to `SELECT COALESCE(SUM(plays), 0) AS plays … WHERE artist = 'Bob Marley'` (https://prql-lang.org/book/). Malloy separates the two kinds of derived field by NAME: "Dimensions are fields representing scalar values" (row-wise: `dimension: full_name is concat(first_name, ' ', last_name)`), measures aggregate (`measure: user_count is count()`) and "may not be used in projections"; both are declared once on the source and reused (https://docs.malloydata.dev/documentation/language/fields).

**E. Plans as inspectable objects (Polars, Mosaic, Substrait).** Polars `explain()` prints the plan bottom-to-top — `FILTER [(col("comment_karma")) > (0)] FROM WITH_COLUMNS: [col("name").str.uppercase()] CSV SCAN …` — and shows the optimized plan where the filter moved into the scan (predicate pushdown) (https://docs.pola.rs/user-guide/lazy/query-plan/). Mosaic's coordinator "collects queries from clients, issues them to DuckDB, and returns the results to clients", with "a query builder API that simplifies the construction of complex queries while enabling query analysis without need of a parser" (https://idl.uw.edu/mosaic/core/); its `Query` objects expose `subqueries`, `clone()`, and only become strings at `toString()` (https://idl.uw.edu/mosaic/api/sql/queries.html). Substrait is "a format for describing compute operations on structured data … designed for interoperability across different languages and systems", split into expressions, relations, extensions (https://substrait.io/).

**F. Logic as JSON with an operator vocabulary (JsonLogic).** `{"and":[{"<":[{"var":"temp"},110]}, {"==":[{"var":"pie.filling"},"apple"]}]}` — "We never eval(). Rules only have read access to data you provide", portable across eight languages (https://jsonlogic.com/).

**G. Lineage as data (OpenLineage, dbt).** OpenLineage's column-lineage facet maps each output column to `inputFields[{namespace,name,field,transformations[{type DIRECT|INDIRECT, subtype IDENTITY|TRANSFORMATION|AGGREGATION | JOIN|GROUP_BY|FILTER|SORT|WINDOW|CONDITIONAL, description, masking}]}]` (https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet). dbt shows a column's upstream columns and labels each hop passthrough / rename / transformation, inheriting descriptions across passthroughs; its caveat: lineage "reflects only select statements, not joins or filters" and Python models cannot be parsed (https://docs.getdbt.com/docs/collaborate/column-level-lineage).

## 2. How each one SHOWS the transform to a person

- **Tableau**: a Calculation Editor dialog (name + formula `SUM([Profit])/SUM([Sales])`, fields in brackets), validated on OK, and the new field lands in the Data pane with an `=` in front of its type icon (https://help.tableau.com/current/pro/desktop/en-us/calculations_calculatedfields_formulas.htm).
- **Power Query**: "Every transformation that is applied to your query is saved as a step in the Applied steps section"; select a step to preview the table as of that step; a step can be renamed and given a description; a diagram view draws one icon per step with dependency lines; the Advanced Editor shows the whole script (https://learn.microsoft.com/en-us/power-query/power-query-ui).
- **Wrangler**: "combines direct manipulation of visualized data with automatic inference of relevant transforms, enabling analysts to iteratively explore the space of applicable operations and preview their effects" (abstract via https://scispace.com/papers/wrangler-interactive-visual-specification-of-data-45jb35e7ux); each suggested transform is shown as a natural-language sentence and the history exports as a script [unverified — not fetched].
- **Polars**: a printed plan; **dbplyr**: `show_query()`; **dbt**: a column graph coloured by hop type.
- **Your own Weave**: "Everything is a column" — `EquationColumn` compiled expressions referencing other columns as named variables and re-triggered when a referenced column's value or statistics changed; grouped transforms were themselves data sources so they composed (/Users/sanjay/github/footprintjs/vizfootprint/docs/research/weave-study.md:307-313). The sheet is that idea returning with provenance attached.

## 3. Comparison on the four axes

| grammar | safety | compile-to-SQL | explainability | shown as |
|---|---|---|---|---|
| Vega expression string | own parser, no eval; still a language to maintain | none built in | opaque string; why() can only say "this formula" | formula text |
| Arquero parsed fn | parse + rewrite; escape() is the leak | none (arquero-worker proves an AST exists) | AST, but JS-shaped | code |
| Plot named reducers | names are data | trivial (`sum`→SUM) | perfect for aggregates, nothing for scalars | option object |
| dbplyr/PRQL verbs | host-language code | the whole point; unknown fns pass through as SQL | show_query | pipeline text + SQL |
| Malloy dimension/measure | own parser | yes | the two-kind split is the explanation | source model |
| JsonLogic tree | no eval, closed operator set | mechanical (one renderer per op) | every node is a named op with named inputs | JSON |
| OpenLineage facet | n/a (a record) | n/a | the target shape of a why() answer | column graph |

## 4. Recommendation for vizfootprint

**Declaration = a small OP TREE (JsonLogic/Vega-window shaped), typed by KIND; the formula bar is a VIEW of it.**

```ts
type DerivedColumn = {
  name: string; table: string;
  kind: 'row' | 'aggregate' | 'window';      // Malloy's dimension/measure split + Vega's window
  expr: Expr;                                 // { op:'div', args:[{col:'profit'},{col:'sales'}] }
  over?: { groupBy?: string[]; sort?: …; frame?: … };   // window only
  requestedBy, intent                         // the commit cause the log already stamps
}
```

- `Expr` = `{col}` | `{lit}` | `{op, args}` over a closed vocabulary (arithmetic, compare, and/or/not, if, string/date helpers, `count|sum|min|max|mean|distinct` — the reducers the fold already has). Closed = no eval (JsonLogic's law), portable, and every node names its inputs, so column lineage (OpenLineage `inputFields`) falls out of the tree for free rather than being parsed back from SQL as dbt must.
- **Two owners per op, one conformance table.** Each op row carries `fold(row-step)` for the memory engine and `sql(args)` for DuckDB/server; a conformance test runs the same expression tree through both and compares (the house PORT + ADAPTER + CONFORMANCE rule). Do not accept a raw-SQL or raw-JS escape hatch in v1: dbplyr's "left as is" pass-through and Arquero's `escape()` are exactly where serialization, why(), and portability break.
- **A derived column referring to a derived column** is a chain, so the memory engine's flowchart gets one stage per column in dependency order (dbplyr's automatic subquery, in stage form); the SQL owner emits nested SELECTs or a WITH chain. Ruling 12 already makes each intermediate a commit.
- **The formula bar** shows Tableau-style text — `[profit] / [sales]` — rendered FROM the tree and parsed BACK by a tiny grammar we own (no JS). Beside it, why() renders the tree as a sentence ("profit divided by sales, per row; reads profit, sales; 3 rows had no sales → absent") — Wrangler's natural-language line, produced from data, not authored.
- **The header**: `=` badge (Tableau), the `kind` badge (row / per group / over window), staleness when a source table's version moved (your CommitRecord.data already carries the versions).
- **The Data Source tab** gets an Applied-Steps strip per table (Power Query) whose steps ARE the ViewQuery + DerivedColumn declarations; click a step = time-travel to the commit that added it; the Polars-style plan view is the footprintjs flowchart itself.
- Keep `kind` explicit rather than inferred: Malloy's rule "measures may not be used in projections" becomes a lint the validator can state in words, and it tells the SQL owner whether to emit `SELECT`, `GROUP BY`, or `OVER (...)`.

Layer 1 owns the tree and the two executors; layer 4 owns the formula bar and step strip; layer 5 owns why() over the tree.

LESSONS
- Declare a derived column as a closed op TREE ({col}|{lit}|{op,args}) rather than an expression string, because JsonLogic shows a closed vocabulary needs no eval and names every input, and Vega/Arquero show that even sandboxed strings and parsed functions still require a language to maintain and leak via escape hatches.
- Give every derived column an explicit kind — row / aggregate / window — because Malloy's dimension-vs-measure rule and Vega-Lite's separate window transform are what let a compiler choose SELECT, GROUP BY, or OVER() and let the validator explain refusals in words.
- Put two owners on each op in one table, fold(row-step) for the memory engine and sql(args) for DuckDB/server, plus a conformance test that runs the same tree through both, because dbplyr's 'unknown functions are left as-is' is where portability silently breaks.
- Use the reducer names the fold already has (count/sum/min/max/mean/distinct) as the aggregate vocabulary, as Observable Plot does, so the aggregate ops of a sheet and of ViewQuery.reduce are one list.
- A derived column that references another derived column becomes an ordered chain — one flowchart stage per column on the memory engine, a nested SELECT or WITH chain in SQL — exactly dbplyr's automatic subquery, and ruling 12 already makes each stage a commit.
- Record column lineage in the OpenLineage shape (output column → inputFields with DIRECT/INDIRECT and a subtype) straight from the tree at declaration time, instead of parsing it back from SQL as dbt must, which is why dbt cannot see joins or filters.
- The formula bar should render Tableau-style text like [profit] / [sales] FROM the tree and parse it back with a tiny grammar we own; the tree, not the text, is the record that why() and the SQL owner read.
- Mark derived columns in the sheet header with an = badge and a kind badge (per row / per group / over window), as Tableau marks calculated fields, and derive staleness from the data versions the commit already stamps.
- Give the Data Source tab a Power Query-style Applied Steps strip per table whose steps ARE the ViewQuery and DerivedColumn declarations; clicking a step is time travel to the commit that added it, and Polars-style explain() is the footprintjs flowchart itself.
- Produce Wrangler-style natural-language descriptions of each step from the declared tree (op names + input columns + the fold's skipped-row counts), never authored prose, so the sentence can never disagree with what ran.
- Do not ship a raw-SQL or raw-JS escape hatch in v1, because Arquero's escape() and dbplyr's sql() are precisely where serialization to workers, compile-to-SQL, and why() all stop working.
- Credit the sheet as the return of Weave's 'everything is a column' EquationColumn idea, now with a declared tree, two engines, and provenance on every column instead of a compiled expression.
